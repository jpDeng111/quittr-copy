# 独立开发者软件工程 Roadmap 与授课提示词

> 项目主线：将现有戒色／冲动管理 App 原型，逐步建设为可以理解、修改、验证、发布和维护的产品。
>
> 学习起点：能跟着 AI 做项目，但独立读写和调试代码还不熟练。
>
> 资料核验日期：2026-09-30。近期案例主要来自 2025—2026 年的一手资料；版本案例不代表安装推荐的最新补丁，实际开课时需重新核验。

## 1. 这条路线培养什么能力

你的目标可以概括为：独立发现值得解决的问题，设计体验，完成工程实现，并根据真实反馈持续改善产品。乔布斯、张小龙、张一鸣可以作为产品判断力和创造力的参照；本课程将这些愿望转化为可以练习的能力，不承诺通过一套课程复制任何人的职业成就。

“10x”在这里表示提高长期有效产出的方向。衡量进步时同时看解决的问题、完成质量、返工、维护成本和用户价值，不用代码行数或 AI 生成量代替能力。

| 能力 | 课程结束时应能展示的证据 |
|---|---|
| 编程与计算机基础 | 读懂数据流；自己修改函数；解释异步、网络、存储和复杂度；定位错误。 |
| 工程设计 | 用清晰边界组织代码；为接口和数据建模；记录技术取舍；逐步重构。 |
| 质量与可靠性 | 编写有效测试；处理失败；从日志定位问题；备份恢复；发布和回滚。 |
| AI 协作 | 写出可验收任务；提供必要上下文；检查补丁；识别错误建议；评估 AI 功能。 |
| 产品与体验 | 从用户情境出发；选择范围；解释交互；根据证据删减或调整功能。 |
| 独立经营 | 估算成本；选择付费价值；处理支持问题；维护依赖；安排可持续迭代。 |

## 2. 从你现有的项目出发

本路线根据当前目录的代码与说明编排，未运行或完整审计应用：

- 前端位于 public/app.js、public/styles.css、public/index.html，使用 React 的浏览器全局加载方式。
- 后端位于 server.js，使用 Node.js 原生 HTTP 服务；package.json 目前只有启动脚本。
- 数据以本地 JSON 文件保存。实际业务包含统计、冲动记录、日记、动机、聊天、屏蔽设置和社区等接口。
- README 的功能说明落后于部分代码。第一阶段就练习核对“文档声称的行为”和“实际实现的行为”。
- “屏蔽网站／App”的界面和服务端设置，不能据此认定已获得系统级拦截能力。课程会专门验证平台权限及真实效果。

学习时使用脱敏或合成数据。第一课先建立可恢复的学习基线；已有未提交修改应妥善保存。以下内容是课程计划，不表示这些功能已经实现或通过测试。

前一份产品课程继续使用：[产品经理课程大纲与授课提示词](../产品经理/产品经理课程大纲与授课提示词.md)。两份课程围绕同一个产品推进，作业可以共享。

## 3. 时间、顺序与产品里程碑

共 40 节主课，分 10 个阶段。每节理论与案例约 60—90 分钟，最低动手任务约 2—4 小时；困难课可以拆成两次。按每周 8—10 小时，预留复习、卡点和真实试用时间，建议安排约 8—12 个月。时间预算是起点假设，第一阶段结束后按实际速度调整。

每课只把“最低任务”作为必做；深入阅读、更多故障组合和第二种技术方案放在完成最低任务后。按能力通过阶段门槛，不因到了某一周就强行进入下一阶段。

| 阶段 | 课次 | 你能交付的产品增量 | 进入下一阶段的条件 |
|---|---|---|---|
| A 接管原型 | 01—04 | 能运行、看懂、修改和调试当前项目 | 独立解释一次请求的路径，完成一个小修复并能恢复修改 |
| B 完成一条功能 | 05—08 | 可使用的“冲动出现 → 获得支持 → 可选记录”流程 | 正常、取消、失败三类状态明确，用户能完成核心任务 |
| C 建立工程基础 | 09—12 | 模块化、类型检查、关键测试和持续集成 | 能从干净环境复现构建，并证明测试能发现故意引入的错误 |
| D 数据正确可靠 | 13—16 | 数据库记录、幂等写入、可靠统计和错误诊断 | 重复请求、日期边界和坏输入不会悄悄污染数据 |
| E 准备受控试用 | 17—20 | 身份与数据隔离、删除导出、备份恢复和测试环境 | 用两个测试账号验证隔离，完成恢复和回滚演练 |
| F 加入 AI 支持 | 21—24 | 服务端 AI 接入、结构化支持、知识检索与可控记忆 | 用户能拒绝、纠正和删除；模型失效时仍有基础支持 |
| G 验证和运行 | 25—28 | AI 评估、成本控制、运行监测和小范围发布 | 有发布条件、回退条件及观察数据，结果有证据可查 |
| H 做成手机 App | 29—32 | 离线能力、提醒、手机核心流程和平台能力验证 | 在真实设备演示核心流程，明确支持范围与权限限制 |
| I 提高工程效率 | 33—36 | 性能分析、可靠后台任务、依赖维护和 AI 协作流程 | 解释优化收益，复现任务失败，并测量 AI 是否真的减少总耗时 |
| J 独立产品交付 | 37—40 | 下一轮用户验证、架构演进、发布候选和毕业答辩 | 另一位开发者能按文档启动，你能独立完成一次变更与事故处理 |

**第一周只做第 01—02 课。**先画清楚现有程序，完成版本控制和恢复练习；第二周再练函数和调试。

### 产品范围如何控制

教学主线先集中在三条价值路径：即时支持、轻量记录、每周回顾。账号、可靠存储、隐私和失败恢复是这些路径的基础设施。社区、排行榜、复杂屏蔽系统、语音陪伴和自动行动代理，需要分别证明价值后才进入产品范围。

支持用户自己选择的减少或停止目标。不要以频率直接诊断，也不要用未经证实的恢复百分比或固定天数承诺效果。工程质量、用户觉得有帮助和临床效果属于不同证据层次。涉及健康内容的知识库应有明确来源和审核责任。

## 4. 技术路线：逐步引入，每种工具都有用途

默认从已有 JavaScript / React / Node 项目演进。第 09 课再逐步引入 TypeScript 与 Vite；保持单一后端、按业务分模块。数据库先学 SQL，再选择产品适合的部署形态。移动端先做一个平台的核心流程，另一平台作为后续移植。

| 引入时机 | 工具或技术 | 要解决的问题 | 选择边界 |
|---|---|---|---|
| 第 01 课 | 编辑器、终端、浏览器 DevTools、curl | 理解代码、请求、进程和错误 | 先掌握断点、Network 和日志，不频繁更换 IDE |
| 第 02 课 | Git、GitHub 或其他 Git 托管 | 小步提交、对比、恢复和协作 | 本地练习先完成，发布仓库前检查私密文件 |
| 第 03／11 课 | node:test；前端需要时用 Vitest；关键流程用 Playwright | 自动验证业务和交互 | 起步只选一个单元测试工具；不同层测试各自负责不同风险 |
| 第 09 课 | TypeScript、Vite、ESLint、格式化工具 | 模块、构建、静态检查和一致性 | 分模块迁移；新版本先读迁移说明 |
| 第 13 课 | SQLite、SQL 客户端；多用户托管时可选 PostgreSQL | 约束、事务、查询、迁移 | 单实例持久磁盘可保留 SQLite；托管部署依条件选择 PostgreSQL，不要求把两套都做一遍 |
| 第 17 课 | 成熟认证库或托管 Auth，例如 Supabase Auth | 身份验证、会话管理 | 用户身份仍需在自己的接口校验；数据隔离不能只靠前端 |
| 第 20 课 | 一个托管平台；需要时用 Docker | 可复现部署、环境配置、持久存储 | 云服务地区、价格和支持在开课时核验；不要求一开始搭 Kubernetes |
| 第 21 课 | 模型服务 SDK 或标准 HTTP 客户端 | 模型调用、超时、错误和成本记录 | 密钥在服务端；模型按中文任务质量、数据处理条款、延迟和成本选择 |
| 第 23—25 课 | SQL 全文检索、JSONL 评估集、简单评估脚本 | 知识查找和可重复质量评估 | 先建立小规模基线，确有收益再加入向量检索与专门平台 |
| 第 27 课 | 结构化日志、错误追踪；需要时用 OpenTelemetry | 定位请求、故障与依赖耗时 | 不把日记原文、聊天原文和令牌写进遥测 |
| 第 29—31 课 | IndexedDB、PWA；React Native + Expo | 离线 Web 与手机 App | React 知识可迁移，但 DOM/CSS 页面不能直接当作原生界面；原生扩展需相应构建环境 |
| 第 32 课 | Xcode / Android Studio、平台官方 API | 验证屏蔽与系统权限能力 | 按目标平台做小实验，审核与权限不可用时设计真实可用的替代路径 |
| 全程，后期加深 | 一个 AI 编码助手、任务说明、diff、评估结果 | 解释、实现、审查和交接 | 前期让 AI 提示和审查；后期才把有边界的任务交给它执行 |

Node 运行时优先选择受支持的 LTS，并核验依赖兼容性；2026-09-30 可将 Node 24 LTS 作为候选。不要照搬旧 README 中“Node 18 或更高”的下限。[Node 发布周期](https://github.com/nodejs/Release)

工具手册：[Node 测试](https://nodejs.org/docs/latest-v24.x/api/test.html)、[Playwright](https://playwright.dev/docs/writing-tests)、[Supabase Auth](https://supabase.com/docs/guides/auth)、[OpenTelemetry](https://opentelemetry.io/docs/concepts/observability-primer/)。框架版本组合以各自官方兼容表为准。

### 本路线采用的方法

| 方法 | 在本项目中的最小实践 | 深入课次 |
|---|---|---|
| 小批量交付与纵向切片 | 一次完成一个从用户操作到数据结果的完整行为 | 05、08、12 |
| 规格驱动开发 | 一页需求、少量行为示例、明确验收，跟随事实更新 | 05、10、36 |
| 测试驱动的局部练习与持续验证 | 对关键规则先写失败样例，修改后证明行为，选择合适测试层次 | 03、11、12 |
| 演进式架构 | 大文件逐步拆分；按已观察到的修改成本引入边界 | 09、13、38 |
| 安全与隐私融入开发 | 在接口、模型、存储和日志设计时确定信任边界 | 10、17—19、24 |
| 上下文工程与编码运行环境 | 给 AI 必要资料、可复现环境、有限任务和可检查结果 | 全程，重点 23、36 |
| 评估驱动的 AI 迭代 | 固定情境集、人工复核、失败保留、比较版本 | 21—28 |
| 可观测性与可靠性工程 | 先定义用户可感知的成功，再用日志、指标和演练判断 | 16、20、26—28 |
| 本地优先与渐进增强 | 网络或模型不可用时保留基础能力，按平台条件增强 | 29—32 |

上述方法按适用范围组合。Spec Kit、Agent 编排等近期工具可以辅助执行；规格错误、验证不足或反馈失真仍需要人来识别。[DORA 2025][N01] 和 [2026 编码工作流研究][N04] 提供了相关观察，但不能证明某一组合适合所有项目。

## 5. 每节课共同采用的学习闭环

1. **预测**：在运行代码前，写下输入、输出、可能的错误。
2. **拆解**：用经典与近期案例理解机制、收益、代价。
3. **亲手做**：自己完成最小修改；卡住时先提出假设，再请 AI 提示。
4. **验证**：展示运行证据，主动制造一个相关失败，观察是否按预期处理。
5. **解释**：不用 AI 代写，说明核心函数、关键取舍和一个替代方案。
6. **提交与复盘**：保留小改动、验收记录和下一步，不把“AI 说完成”当作完成。

每课提交：一个可审查的改动或设计产物、一份验收证据、200—400 字复盘。案例阅读、开放问题和产品判断也属于任务，不要求每课都安装一个新工具。

下文 C 编号对应经典来源，N 编号对应近期来源，完整链接见文末。课堂中的对比和项目任务是教学设计，不是来源已经证明的产品效果。

## 6. 40 节课详细路线

### 阶段 A：接管现有原型

#### 01｜一条用户操作怎样穿过整个程序

- **理论与技术分析**：文件、进程、端口、浏览器与服务器；沿“点击 → fetch → 路由 → 读取 → 响应 → 渲染”追踪一次统计请求。
- **经典案例**：[TodoMVC][C01] 的输入、状态与视图，观察一个小程序如何完整工作。
- **近期案例**：[长任务编码环境，2025][N03]，分析为什么初始化说明和可复现启动会影响后续工作。
- **工具实操**：终端、编辑器跳转、DevTools Network、curl；认识 npm start 实际执行什么。
- **开放问题**：页面看起来正常，哪些环节仍可能没有真正工作？你如何证明？
- **最低任务与验收**：画出当前项目请求链路，标出 5 个关键位置；记录启动、一个成功请求和一个失败请求；建立“已证实功能／演示占位／外部依赖／内容待核验”清单，纠正一处 README 差异。
- **思维训练**：把“我觉得”换成“我在哪个文件／请求里观察到”。

#### 02｜Git、环境与可恢复的修改

- **理论与技术分析**：工作区、暂存区、提交、分支与差异；依赖、环境变量和运行环境；代码备份与业务数据备份的区别。
- **经典案例**：[Git 的快照模型][C02]，分析为什么提交不是简单保存文件。
- **近期案例**：[npm 可信发布，2025—2026][N10]，初步理解发布身份与长期令牌的差别，深入部分留到第 35 课。
- **工具实操**：git status、diff、add、commit、log；在练习分支进行恢复，建立不含密钥的环境示例。
- **开放问题**：为何“只有我一个人开发”仍需要提交记录？哪些数据不应放入仓库？
- **最低任务与验收**：妥善保存已有修改；提交一处说明改进，并在练习分支恢复它；证明私密配置和运行数据没有混入这次提交。
- **思维训练**：把每个提交写成“解决什么问题、怎样确认”。

#### 03｜JavaScript、数据结构与可验证的小函数

- **理论与技术分析**：值与引用、条件、循环、函数、对象、数组、Map；把界面计算抽成输入输出明确的函数，认识线性扫描。
- **经典案例**：[TodoMVC][C01] 的添加、完成和筛选，分析直接修改对象与返回新状态的区别。
- **近期案例**：[TypeScript 6.0，2026][N07]，观察更严格的类型检查如何提前暴露问题；本节先写 JavaScript。
- **工具实操**：Node REPL、编辑器断点、node:test；在内存中使用合成记录。
- **开放问题**：同一个“天数”为什么可能出现字符串、数字和无效值？该在哪个边界处理？
- **最低任务与验收**：自己写一个按日期筛选记录的纯函数，检查空数组、无效日期和边界日期；不用 AI 代写解释每一步。
- **思维训练**：先手算三组输入输出，再运行代码。

#### 04｜异步、事件循环与系统调试

- **理论与技术分析**：Promise、async/await、调用栈、异步 I/O、异常；理解请求先发后到和界面过期数据。
- **经典案例**：[AWS 超时与重试][C05] 的远程调用情境，区分本地异常和远端未响应。
- **近期案例**：[Cloudflare 2025-09-12 事故][N23]，先分析一次不稳定对象引用怎样触发重复请求；系统负载与重试部分在第 26 课深入。
- **工具实操**：Network 限速、断点、调用栈、console.time；模拟慢请求。
- **开放问题**：两次请求倒序返回时，哪次结果应该显示？“再试一次”会有什么副作用？
- **最低任务与验收**：在练习页面复现一次响应乱序，用请求标识或取消机制处理；提交“现象 → 假设 → 实验 → 结论”的调试记录。
- **思维训练**：每次只改变一个变量。

### 阶段 B：完成一条真正可用的功能

#### 05｜把需求写成可以判断对错的规格

- **理论与技术分析**：用户情境、领域词汇、范围、前置条件、验收标准；用事件与状态描述“获得即时支持”。
- **经典案例**：[TodoMVC 的应用规格][C01]，分析同一需求怎样约束不同实现。
- **近期案例**：[GitHub Spec Kit，2025／2026][N02]，拆解从规格到计划和任务的流程；先用一页 Markdown 实践。
- **工具实操**：Markdown、简单流程图、任务列表；区分必须满足的行为和待验证假设。
- **开放问题**：怎样避免规格越写越大，却没有降低实现中的不确定性？
- **最低任务与验收**：写一页即时支持规格，含正常、取消、失败场景及 5 条可观察的验收标准；删去至少一个非必要功能并解释。
- **思维训练**：将形容词“智能、温暖、好用”改成可观察行为。

#### 06｜语义化页面、CSS 与组件边界

- **理论与技术分析**：HTML 语义、盒模型、布局、组件、props；理解 React 渲染与普通 DOM 操作的关系。
- **经典案例**：[Thinking in React][C03] 的筛选表格，按职责而非外观任意切组件。
- **近期案例**：[Safari 18.4，2025][N18] 的 Web 平台改进，讨论功能检测与渐进增强。
- **工具实操**：Elements、Computed Styles、设备尺寸模拟；用已有 React 拆出一个组件。
- **开放问题**：什么时候复用组件能减少复杂度，什么时候会制造一堆难懂参数？
- **最低任务与验收**：完成即时支持入口和行动选择组件；在窄屏与键盘操作下可使用，按钮具有明确名称。
- **思维训练**：解释一处布局为什么会溢出，而不只尝试随机改样式。

#### 07｜状态机与不会相互矛盾的界面

- **理论与技术分析**：状态、事件、转换、不变量；局部状态与服务端状态；避免多个布尔值组成不可能状态。
- **经典案例**：[React 状态组织示例][C03]，分析重复保存的状态如何失去同步。
- **近期案例**：[Lily 的结构化对话设计，2025][N15]，观察自由表达如何放进有开场和结束条件的流程。
- **工具实操**：状态转换表、React state/reducer；本课不必安装状态机库。
- **开放问题**：用户中途离开再回来，哪些状态应保留，哪些应重新开始？
- **最低任务与验收**：实现待开始、进行中、完成、取消、失败五种状态；列出不允许的转换并实际尝试。
- **思维训练**：用“必须始终成立的条件”描述程序。

#### 08｜纵向完成：从操作到记录再到反馈

- **理论与技术分析**：纵向切片、渐进反馈、可访问性、错误恢复；理解一条功能如何跨越页面、接口和存储。
- **经典案例**：[Thinking in React][C03] 的单向数据流；结合 TodoMVC 观察状态更新到视图的过程。
- **近期案例**：[Playwright 测试代理的 TodoMVC 示例，当前文档][N16]，分析“可执行步骤”是否覆盖真正的用户目的。
- **工具实操**：浏览器、合成数据、手工验收脚本；早期不要求复杂端到端套件。
- **开放问题**：用户已经获得帮助但不想记录，这条流程算不算完成？
- **最低任务与验收**：贯通“打开支持 → 选择行动 → 可选保存”；演示成功、跳过、网络失败，保留一段操作记录。
- **思维训练**：以用户得到的结果定义完成，而不是数完成了几个页面。

### 阶段 C：建立可以持续修改的工程基础

#### 09｜模块、TypeScript 与构建工具

- **理论与技术分析**：模块边界、导入导出、运行时与编译时、开发构建与生产构建；逐步迁移而非一次重写。
- **经典案例**：[Strangler Fig 渐进替换][C10]，分析怎样保持旧功能可用同时替换一小部分。
- **近期案例**：[Vite 8／8.1，2026][N08] 与 [TypeScript 6.0][N07]，讨论构建链变化、兼容性与迁移成本。
- **工具实操**：Vite、TypeScript、ESLint、lockfile；观察依赖图和构建输出。
- **开放问题**：什么时候类型帮助你发现设计问题，什么时候复杂类型掩盖了简单业务？
- **最低任务与验收**：只迁移一个功能模块；开发启动与生产构建都通过；保留迁移前后的行为证据和回退办法。
- **思维训练**：为一个新工具写“引入成本、实际收益、退出方式”。

#### 10｜HTTP、API 契约与输入边界

- **理论与技术分析**：方法、状态码、请求体、响应体、序列化、校验；静态类型不能代替服务端验证。
- **经典案例**：[Stripe API 的幂等请求][C04]，观察接口如何把不可靠网络中的意图表达清楚。
- **近期案例**：[OWASP ASVS 5.0，2025][N20] 的输入与边界要求，练习将要求落实到一个接口。
- **工具实操**：curl、Network、JSON Schema 或一个校验库；写最小接口说明。
- **开放问题**：缺失、空字符串和 null 是否代表同一件事？错误响应应向用户泄露多少内部信息？
- **最低任务与验收**：为一条记录接口定义并实现契约；检查正常、缺字段、错误类型、过长输入，保证坏输入不落盘。
- **思维训练**：先解释边界，再选库。

#### 11｜测试为什么能提供信心

- **理论与技术分析**：单元、接口、端到端测试；测试替身；行为断言；用一个回归问题体验先失败再修复的过程。
- **经典案例**：[SQLite 的测试与崩溃验证][C06]，分析为什么只检查成功路径无法保证可靠。
- **近期案例**：[Playwright 测试代理][N16]，审查自动生成的测试是否通过删断言、跳过失败来“修好”结果。
- **工具实操**：node:test 或 Vitest、Playwright trace；选少量重要路径。
- **开放问题**：测试全绿而产品仍坏掉，可能是哪一层的证据缺失？
- **最低任务与验收**：给统计逻辑、记录接口和核心流程各选一个有价值的测试；故意引入对应错误，证明测试能抓到。
- **思维训练**：解释“这个断言失败意味着什么”，而不追求测试数量。

#### 12｜持续集成与可复现交付

- **理论与技术分析**：持续集成、短分支、小批量、构建产物；区分开发机状态和干净环境。
- **经典案例**：[Git 分支与合并][C02]，用最小冲突练习理解协作边界。
- **近期案例**：[DORA 2025][N01]，讨论 AI 产出增加时，验证与交付能力为什么也需要提高。
- **工具实操**：GitHub Actions 或等价 CI；依赖锁定、检查、测试、构建。
- **开放问题**：一次只提交很少代码，为什么可能更快完成整个功能？
- **最低任务与验收**：建立一条 CI；演示正确提交通过、故意失败被拦截，以及新检出目录能复现结果。
- **思维训练**：区分“运行过”和“任何人都能重现”。

### 阶段 D：让数据与统计值得信任

#### 13｜从 JSON 文件到数据库

- **理论与技术分析**：表、主键、外键、约束、索引、查询与迁移；先写 SQL，理解 ORM 试图省去什么。
- **经典案例**：[SQLite 原子提交][C06]，分析数据库在失败条件下提供的保证。
- **近期案例**：[PostgreSQL 18，2025][N13] 的查询观测改进，用来理解为什么需要读执行计划。
- **工具实操**：SQLite、SQL 客户端、迁移脚本；多用户托管的 PostgreSQL 是后续条件选择。
- **开放问题**：哪些约束必须由数据库守住，不能只靠界面判断？
- **最低任务与验收**：把一个类型的合成记录迁入表；验证条数与关键字段一致，重复执行迁移不会重复导入。
- **思维训练**：说明为什么每一个字段存在。

#### 14｜并发、事务与幂等

- **理论与技术分析**：读改写冲突、事务、唯一约束、幂等键；原子替换文件并不自动提供多次请求间的事务隔离。
- **经典案例**：[Stripe 幂等请求][C04]，分析“服务已完成但响应丢失”的重试。
- **近期案例**：[Cloudflare 2025-11-18 事故][N12]，研究一次上游数据变化怎样传播，区分局部正确和系统正确。
- **工具实操**：并发请求小脚本、SQL 事务和唯一约束。
- **开放问题**：同一个按钮被点两次，怎样区分重复请求与用户真的想记录两次？
- **最低任务与验收**：给记录接口添加幂等策略；用同键重复请求、不同键请求和失败重试验证实际保存数量。
- **思维训练**：画两个请求交错执行的时间线。

#### 15｜日期、时区、统计与算法

- **理论与技术分析**：时间点与本地日期、时区、跨日、排序与分组、复杂度；区分产品口径和技术计算。
- **经典案例**：[SQLite 日期函数][C07]，对照 UTC 与本地日期查询解释边界。
- **近期案例**：[PostgreSQL 18][N13] 的 EXPLAIN 信息，练习用测量比较“每次全量排序”和“索引筛选”。
- **工具实操**：固定时钟、表驱动测试、SQL 查询计划；用合成跨日数据。
- **开放问题**：用户出差换时区后，“今天”和“连续一天”的定义是否应该改变？
- **最低任务与验收**：为一项周统计写清口径，覆盖跨日、重复、无记录和用户时区；记录小数据与较大数据的耗时。
- **思维训练**：先判断算的指标是否有意义，再优化速度。

#### 16｜错误处理与可诊断性

- **理论与技术分析**：业务错误、程序错误、依赖错误；错误分类、请求标识、结构化日志和保留上下文。
- **经典案例**：[Google SRE 监测][C08]，区分用户看到的故障和内部原因。
- **近期案例**：[Cloudflare 2025 事故复盘][N12]，观察时间线和线索如何帮助定位而不是猜测。
- **工具实操**：日志检索、请求 ID、错误边界；主动注入坏输入或依赖失败。
- **开放问题**：日志记得越多是否越容易排障？敏感原文、密钥和错误堆栈应如何处理？
- **最低任务与验收**：让三个不同错误产生可区分的反馈；凭一个请求 ID 找到失败环节，同时确认日志不含私密原文。
- **思维训练**：把错误当作需要设计的输入，而不是意外。

### 阶段 E：准备可以恢复的受控试用

#### 17｜认证、授权与用户隔离

- **理论与技术分析**：身份与权限、会话生命周期、服务端校验、对象归属；根据 Web／移动端形态选择会话策略。
- **经典案例**：[OWASP 授权示例与原则][C11]，理解“知道记录 ID”不等于“有权读取”。
- **近期案例**：[ASVS 5.0，2025][N20]，把访问控制要求转成测试场景。
- **工具实操**：成熟 Auth 方案、两个测试账号、接口请求；不自己实现密码学协议。
- **开放问题**：前端隐藏按钮为何不能提供权限保证？管理员应该能看到私密日记吗？
- **最低任务与验收**：接入一种身份方案，限制记录归属；验证 A 无法读写 B 的数据，过期会话有明确行为。
- **思维训练**：从“攻击者直接调用接口”检查系统假设。

#### 18｜威胁建模与隐私设计

- **理论与技术分析**：资产、入口、信任边界、最小权限、输出编码、请求伪造；区分加密传输、静态加密和端到端加密。
- **经典案例**：[OWASP 授权与安全指南][C11]，对用户输入到展示的路径逐层分析。
- **近期案例**：[React Server Components 2025—2026 漏洞通告][N11]，学习先核对受影响组件与前提，再制定应对；当前客户端 React 原型不能仅凭名称判定受影响。
- **工具实操**：数据流图、浏览器存储检查、依赖清单、环境变量管理。
- **开放问题**：为了个性化必须保留什么？产品承诺“私密”需要哪些可验证机制？
- **最低任务与验收**：为日记与 AI 调用画信任边界，选前三个真实风险各落实一个控制，并给出验证步骤。
- **思维训练**：根据影响和证据排序风险。

#### 19｜导出、删除、迁移和恢复

- **理论与技术分析**：备份、恢复点、恢复时间、数据版本、删除范围；理解活动数据、缓存、模型上下文和备份中的不同生命周期。
- **经典案例**：[GitLab 2017 数据库事故][C09]，分析为什么存在备份不等于能够恢复。
- **近期案例**：[Apple Foundation Models，2025][N14]，讨论哪些处理可留在设备端，以及这会怎样改变数据流。
- **工具实操**：备份／恢复脚本、合成数据库、导出格式和删除记录。
- **开放问题**：用户删掉一条记忆后，如何避免它从摘要、旧备份或其他设备重新出现？
- **最低任务与验收**：在隔离环境导出、删除、恢复合成数据，核对数量与字段；写出备份保留和删除边界。
- **思维训练**：分别定义“我有文件”和“我能恢复服务”的证据。

#### 20｜第一次部署与回滚

- **理论与技术分析**：DNS、HTTPS、环境配置、持久卷、健康检查、部署产物、迁移与回滚；开发与生产环境分离。
- **经典案例**：[Google SRE 的小范围发布][C08]，学习把风险限制在小范围内。
- **近期案例**：[Cloudflare Fail Small 计划][N12]，讨论故障传播范围与恢复机制。
- **工具实操**：一个托管平台、CI、部署日志；需要时才使用 Docker。
- **开放问题**：代码回滚了，数据库结构能否一起回滚？哪些迁移应该先保持向后兼容？
- **最低任务与验收**：部署受控测试环境，先用合成数据；演示重启后数据仍在，以及回滚到上一版本；真实用户试用前满足 17—19 课的条件。
- **思维训练**：用一次演练检验运维说明。

### 阶段 F：把 AI 变成可控的产品功能

#### 21｜选择 AI 任务与设计模型访问层

- **理论与技术分析**：规则、固定内容、检索、生成的分工；模型输入输出、服务端密钥、超时、调用配额和适配层。
- **经典案例**：[AWS 远程调用可靠性][C05]，把模型看作可能变慢或失败的外部依赖。
- **近期案例**：[Apple Foundation Models，2025][N14]，比较端侧与云端模型在功能、设备覆盖、隐私和成本上的取舍。
- **工具实操**：现有模型代理、HTTP 客户端、模拟模型；实际模型以开课时可用服务和数据处理条件为准。
- **开放问题**：如果固定内容已经能提供有用支持，加入生成模型的增量价值在哪里？
- **最低任务与验收**：先用相同情境比较固定内容与生成内容，再实现统一调用接口；证明成功、超时和无配额都有清晰结果。
- **思维训练**：用一个可观察收益为 AI 功能辩护，也允许结论是暂不启用。

#### 22｜结构化输出与有边界的对话

- **理论与技术分析**：输出 schema、解析校验、对话状态、工具权限；合法 JSON、符合结构和内容正确是三个层次。
- **经典案例**：[Google PAIR][C13] 的控制、反馈和失败恢复，分析用户如何理解系统能力。
- **近期案例**：[Lily 对话设计，2025][N15]，学习如何在有目的的流程中允许自然表达。
- **工具实操**：JSON Schema 或校验库、提示词版本、对话回放样例。
- **开放问题**：模型建议修改用户目标时，为什么不能直接把建议写成已生效状态？
- **最低任务与验收**：让支持助手返回“简短回应、可选行动、下一步问题”；对格式错误、无效行动和用户拒绝做处理，核心记录只经确定性业务逻辑修改。
- **思维训练**：区分生成建议与执行授权。

#### 23｜知识库、检索与上下文选择

- **理论与技术分析**：检索增强生成、关键词检索、分块、来源、召回和相关性；上下文长度与噪声的取舍。
- **经典案例**：[SQLite FTS5 全文检索][C17] 的匹配和排序，理解先检索再使用的机制。
- **近期案例**：[上下文工程，2025][N19]，分析为什么把全部历史塞进提示词未必得到更可靠结果。
- **工具实操**：一小组有来源且可使用的内容卡、SQLite FTS5、检索测试表；向量检索作为比较实验。
- **开放问题**：知识库内容包含命令式文本时，如何保持它是资料而不是系统指令？
- **最低任务与验收**：为 10—20 张内容卡建立简单检索，测试 10 个问题；回答能关联来源，找不到支持材料时明确处理。
- **思维训练**：分别判断“检索错了”和“生成错了”，再选择修复位置。

#### 24｜用户记忆、行为反馈与个性化

- **理论与技术分析**：显式偏好、观察、推断、摘要、过期和撤回；相关性不能直接解释行为原因。
- **经典案例**：[Google PAIR 的反馈与控制][C13]，研究用户怎样纠正系统而不必理解模型内部。
- **近期案例**：[Lily 的对话记忆，2025][N15]，拆解记忆选择及其对下一次体验的影响。
- **工具实操**：记忆表、来源字段、用户确认界面、最小规则推荐；先不用复杂推荐算法。
- **开放问题**：连续几次在深夜记录，能否断言用户的冲动由深夜引起？还缺什么证据？
- **最低任务与验收**：实现一个用户确认的偏好及其推荐效果；用户可查看、纠正、删除；删除后下一轮上下文不再包含该偏好。
- **思维训练**：给每条推断标明证据与不确定性。

### 阶段 G：验证 AI、控制成本并运行产品

#### 25｜AI 评估与回归集

- **理论与技术分析**：确定性测试与模型评估、评分规则、重复试验、人工复核、保留测试集；不把一次好回答当稳定能力。
- **经典案例**：[SQLite 多种测试方法][C06]，迁移“从不同角度发现失败”的思想，而不是照搬数据库规模。
- **近期案例**：[Anthropic Agent 评估实践，2026][N05]，区分输出、执行轨迹和最终状态。
- **工具实操**：JSONL 场景集、简单评估脚本、人工评分表；先建立可读的基线。
- **开放问题**：模型当裁判时，怎样发现它偏爱流畅但没有帮助的回答？
- **最低任务与验收**：构造 20 个合成情境，覆盖错误记忆、用户纠正、来源不足、自责、格式错误和失败恢复；比较两版提示词，保留全部失败样例。
- **思维训练**：定义关键失败项，不让平均高分掩盖严重错误；技术评估不充当疗效证明。

#### 26｜流式响应、取消、重试与成本

- **理论与技术分析**：首段响应时间、完整响应时间、流式传输、取消传播、退避、限流、每次任务成本。
- **经典案例**：[AWS 重试与抖动][C05]，分析多个层级同时重试造成的放大。
- **近期案例**：[Cloudflare 2025-09-12 事故][N23]，从 React Effect 中不稳定对象引用引发重复请求，追踪到系统负载。
- **工具实操**：AbortController、网络限速、模拟 429／超时、模型用量记录；确认服务商对取消与计费的实际行为。
- **开放问题**：用户关掉页面后，后端调用是否会自动停止？重试一次可能花多少成本？
- **最低任务与验收**：为一次 AI 请求实现用户取消、总超时和有限重试；记录三次不同失败下的实际请求次数，并设置用户级预算上限。
- **思维训练**：先数清实际调用次数，再讨论速度和成本。

#### 27｜可观测性、服务目标与事故复盘

- **理论与技术分析**：日志、指标、追踪；延迟、错误率、可用性目标和告警；区分用户症状与依赖原因。
- **经典案例**：[Google SRE][C08]，从用户可感知的服务行为确定观察对象。
- **近期案例**：[OpenTelemetry AI 观测实践，2025][N24]，追踪一次模型调用；GenAI 约定更新较快，实施时查当前规范。
- **工具实操**：请求 ID、结构化日志、一个错误追踪工具；需要跨边界诊断时再加 trace。
- **开放问题**：模型失败但固定支持仍可用，这次请求算整体失败还是部分降级？
- **最低任务与验收**：为记录和 AI 支持分别定义成功口径；注入一次依赖超时，靠观测数据定位并写无责复盘。
- **思维训练**：把“谁写错了”转化为“哪些条件让错误影响了用户”。

#### 28｜功能开关、小范围发布与用户结果

- **理论与技术分析**：功能开关、灰度、回退、曝光记录、任务完成指标、选择偏差；服务可靠和功能有价值需分别验证。
- **经典案例**：[Google HEART][C14] 与 [SRE 小范围发布][C08]，分别回答用户结果与发布风险。
- **近期案例**：[Cloudflare 2025-12-05 事故][N25]，分析关闭功能时下游仍假定对象存在的失败。
- **工具实操**：简单配置开关、最少必要埋点、受控试用反馈；不必先买完整实验平台。
- **开放问题**：用户更少打开 App，哪些证据能区分状态改善和放弃使用？
- **最低任务与验收**：让 AI 功能可以安全关闭；写明小范围启用、观察和回退条件，先用合成数据验证开关前后的完整路径。
- **思维训练**：把“统计显著”“用户觉得有帮助”“足以继续投资”分开判断。

### 阶段 H：从 Web 进入真实手机环境

#### 29｜离线、本地优先与同步冲突

- **理论与技术分析**：本地状态、缓存、待同步队列、版本、冲突和删除标记；离线可用与多端一致是不同问题。
- **经典案例**：[Ink & Switch Local-first，2019][C12]，研究数据所有权、离线体验和同步复杂度。
- **近期案例**：[Apple 端侧模型框架，2025][N14]，讨论没有网络时哪些体验可以继续、哪些能力需要明确降级。
- **工具实操**：IndexedDB、DevTools 离线模式、两份浏览器会话；先实现单用户离线记录。
- **开放问题**：设备 A 删除、设备 B 离线修改同一条记录，重新联网后应怎样处理？
- **最低任务与验收**：离线新增一条记录，重启页面仍保留，联网后只同步一次；为删除与编辑冲突写明确策略，不要求本节自研 CRDT。
- **思维训练**：把同一场景放进“断网、重启、乱序”三个条件再检查。

#### 30｜PWA、提醒与后台限制

- **理论与技术分析**：安装、应用生命周期、Service Worker、推送权限、缓存更新；后台计时器与可靠提醒的区别。
- **经典案例**：[Service Worker 生命周期与离线示例][C16]，观察旧缓存为何可能让用户长期运行旧版本。
- **近期案例**：[WebKit Declarative Web Push，2025][N18]，研究声明式推送和脚本失败时的回退；支持范围需真机核验。
- **工具实操**：manifest、缓存检查、真实手机浏览器、通知权限设置。
- **开放问题**：提醒可能在锁屏暴露什么？如果用户关闭通知，产品还能怎样提供价值？
- **最低任务与验收**：让 Web 核心流程在目标手机以可安装方式运行，验证离线入口和更新；提醒先完成一个可撤销的权限／发送实验，失败时写明原因。
- **思维训练**：以真实设备行为纠正桌面模拟器带来的假设。

#### 31｜跨平台 App、导航与设备生命周期

- **理论与技术分析**：Web 与原生渲染差异、组件复用边界、导航、前后台切换、本地存储、构建与签名的基本概念。
- **经典案例**：[React 组件与状态模型][C03]，分析业务逻辑能复用而页面实现可能需要重做的原因。
- **近期案例**：[Expo SDK 55，2026][N09]，学习 SDK、React Native、React 的版本配套以及 development build 的用途。
- **工具实操**：React Native + Expo、一个目标平台的真机、官方诊断与构建工具；具体安装版在开课时确认。
- **开放问题**：使用跨平台框架后，哪些成本仍需要按 iOS 和 Android 分别支付？
- **最低任务与验收**：迁移即时支持与记录两条流程到一个平台；真机演示返回、切后台、恢复和网络失败。允许本课拆成两个工作单元。
- **思维训练**：写一份基于项目约束的技术选型决定，而不是框架排行榜。

#### 32｜内容屏蔽：验证系统能力

- **理论与技术分析**：App 沙箱、系统授权、扩展、分发权限；区分 App 内过滤、域名限制、系统使用限制与网络过滤。
- **经典案例**：[Apple Screen Time API 的 Worklog 示例，2022][C15]，研究个人授权、Managed Settings 和用户撤回。
- **近期案例**：[WWDC25 NetworkExtension URL 过滤][N17]，分析它与 Screen Time 的能力、实现成本和适用范围差别。
- **工具实操**：选一个目标平台，阅读官方示例，使用 Xcode 或 Android Studio 做时间受限的验证；跨平台 UI 不会自动获得这些权限。
- **开放问题**：用户能撤销限制，产品如何仍然提供帮助？“已保护”的文案需要什么证据？
- **最低任务与验收**：用无害测试目标完成一项授权／限制／撤回实验，提交能力矩阵和真机证据；缺少硬件或 entitlement 时提交可复现实验与明确阻塞，不能宣称已实现拦截。
- **思维训练**：把高风险依赖先做成小实验，再决定是否纳入正式产品。分发前核验 [Family Controls 权限要求](https://developer.apple.com/documentation/familycontrols/requesting-the-family-controls-entitlement)。

### 阶段 I：提高性能、维护能力和 AI 协作效率

#### 33｜性能分析、复杂度与容量

- **理论与技术分析**：CPU、内存、I/O、主线程、缓存、索引；延迟分布、代表性负载、重复测量和性能预算。
- **经典案例**：[SRE 的延迟与饱和度][C08]，先观察瓶颈，再决定优化位置。
- **近期案例**：[Vite 8.1，2026][N08] 的实验性开发模式和特定负载测量，讨论开发构建速度与最终用户体验为何需分别测量。
- **工具实操**：Performance、内存快照、SQL EXPLAIN、合成数据脚本；只压测自有测试环境。
- **开放问题**：缓存能让一次请求变快，同时引入哪些失效和私密数据风险？
- **最低任务与验收**：找到一个真实瓶颈，记录修改前后至少五次同条件测量；解释复杂度、内存或 I/O 的变化及代价。
- **思维训练**：允许测量结论否定最初的优化猜想。

#### 34｜后台任务、Webhook 与订阅权益

- **理论与技术分析**：异步任务、至少一次投递、去重、签名验证、重试和死信；把付款状态与产品权益分开建模。
- **经典案例**：[Stripe 幂等请求及 Webhook][C04]，观察重复事件、乱序到达和重放处理。
- **近期案例**：[Cloudflare 2025-09-12 事故][N23]，分析重试如何放大问题，迁移到后台任务的请求预算。
- **工具实操**：简单数据库任务表或托管队列、Webhook 本地测试、支付沙箱；无需立即收费。
- **开放问题**：退款、取消续费与当前权益到期是否同一事件？收到事件顺序错误怎么办？
- **最低任务与验收**：先用模拟订阅事件实现一个权益状态机，验证重复、乱序和失败重试；真实支付接入在选定地区与平台后决定。
- **思维训练**：为每个外部事件写清“可重复执行会怎样”。

#### 35｜依赖、供应链、升级与维护

- **理论与技术分析**：直接与传递依赖、lockfile、语义版本、漏洞影响面、发布身份、升级验证和许可证。
- **经典案例**：[Git 内容与历史模型][C02]，理解如何定位版本差异、回归来源和恢复路径。
- **近期案例**：[npm 2026 暂存发布及安装控制][N10] 与 [React 安全更新][N11]，分别学习构建来源和受影响组件判断。
- **工具实操**：依赖清单、官方安全公告、更新工具、干净构建与回归测试。
- **开放问题**：扫描器报了严重漏洞，但对应功能并未部署，如何形成有依据的处置决定？
- **最低任务与验收**：完成一次受控依赖升级，记录选择版本、变更、验证和回退；画出代码从依赖来源到部署产物的路径。
- **思维训练**：既不忽略告警，也不把数量当作风险判断。

#### 36｜规格驱动与 AI 编码工作流

- **理论与技术分析**：可执行规格、上下文管理、任务隔离、评审职责、运行证据；自动化流程本身也需要成本和效果判断。
- **经典案例**：[Git 的小步变更][C02] 与 [SQLite 的独立验证思想][C06]，构建“提出改动与验证改动”的清晰关系。
- **近期案例**：[Spec Kit][N02]、[2026 长任务编码实践][N04] 和 [METR 2026 实验反思][N21]，比较结构化协作与计时偏差。
- **工具实操**：一个 AI 编码助手、任务规格、Git diff、检查脚本；完成手动闭环后，可选用 Spec Kit；多代理只做比较实验。
- **开放问题**：AI 节省了输入代码时间，却增加了阅读和返工时间，这次协作是否更有效？
- **最低任务与验收**：给 AI 一项边界清楚的小任务，自己评审并修复；记录规划、生成、阅读、修改、验证总耗时，与相近的手动任务比较，说明小样本局限。
- **思维训练**：评估整个交付周期，不仅看生成速度。

### 阶段 J：成为能持续交付产品的独立开发者

#### 37｜用户反馈、产品实验与范围控制

- **理论与技术分析**：访谈与行为证据、目标指标、反向指标、选择偏差、机会成本；用证据选择下一步。
- **经典案例**：[Google HEART，2010][C14]，把产品目标映射到用户信号和指标。
- **近期案例**：[DORA 2025][N01] 与 [METR 2026][N21]，讨论度量对象、选择偏差和效率感知。
- **工具实操**：最少必要的产品事件、反馈表、决策记录；邀请自愿参与的成年人，任务可使用虚构情境。
- **开放问题**：用户提出十个功能，你怎样决定先做哪个？保留哪个功能可能反而降低产品价值？
- **最低任务与验收**：整理一轮小规模试用的证据；选择一个继续、一个修改、一个暂缓的决定，各写理由和仍缺的信息。不能招募时明确标为模拟练习。
- **思维训练**：寻找能够推翻自己产品假设的证据。

#### 38｜架构演进与技术债

- **理论与技术分析**：内聚、耦合、边界、依赖反转、模块化单体、迁移、架构决策记录；何时拆分服务需要实际证据。
- **经典案例**：[Strangler Fig][C10]，逐步替换实现并保持功能连续。
- **近期案例**：[Vite 8 的构建架构演进，2026][N08]，分析统一工具链的收益及生态兼容成本，避免把大项目方案直接照搬。
- **工具实操**：模块依赖图、ADR、一个适配接口、迁移／回退记录。
- **开放问题**：什么迹象说明该重构？“代码看起来不优雅”和“修改成本正在上升”如何区分？
- **最低任务与验收**：选一个已观察到的维护痛点进行有测试保护的重构；展示行为未变、边界更清楚，并说明没有采用的更复杂方案。
- **思维训练**：把技术债写成未来可能支付的具体成本。

#### 39｜发布、收费、支持与持续维护

- **理论与技术分析**：版本、分发、发布说明、平台隐私披露、订阅恢复、支持渠道、运行成本；收费必须与明确价值对应。
- **经典案例**：[GitLab 2017 复盘][C09] 与 [SRE 发布实践][C08]，分析恢复能力与透明说明如何支撑信任。
- **近期案例**：[Expo SDK 55 的版本与分发说明，2026][N09]，区分本地能运行、开发构建可用和商店可分发。
- **工具实操**：一个目标商店的测试分发／沙箱、构建产物、问题追踪和成本表；价格及目标市场规则在本课核验。
- **开放问题**：哪些支持能力应保持基础可用？AI 调用成本翻倍时，付费方案怎样维持？
- **最低任务与验收**：产出一个发布候选包、发布说明、支持流程和成本估算；满足平台条件时进入受控测试分发，否则记录具体阻塞和可演示替代物。
- **思维训练**：同时计算用户收益、维护时间和每月现金成本。

#### 40｜毕业：完整交付与陌生问题实战

- **理论与技术分析**：从需求到运行的完整生命周期；如何证明产品、代码、数据、AI 与运维形成一致的系统。
- **经典案例**：[SQLite 的失败验证][C06] 与 [GitLab 恢复复盘][C09]，检验在正常条件外系统是否仍可解释、可恢复。
- **近期案例**：[Anthropic 2026 编码技能形成研究][N22] 与 [长任务工程评估][N04]，讨论“完成任务”和“掌握能力”的差异。
- **工具实操**：项目仓库、构建与测试命令、真机、运行手册、数据备份、日志。
- **开放问题**：如果只能保留三个功能，你会留下什么？如果六个月后交给别人维护，最难解释的地方在哪里？
- **最低任务与验收**：演示完整核心流程；让另一人按文档启动，或自己在干净环境复现；独立定位一个此前没见过的缺陷、恢复一份合成备份、解释一次 AI 错误及回退。
- **思维训练**：用证据总结“现在能独立做什么、还需要什么帮助”，写下一阶段 90 天计划。

## 7. 如何确认自己确实学会了

### 每阶段都做一次不依赖完整 AI 答案的检查

- **读代码**：解释一段关键代码的输入、状态变化、输出和失败条件。
- **做变更**：在已有功能上处理一个小变化，例如统计时区改变、用户取消请求或字段变为可选。
- **调试**：先复现，再写至少两个假设，通过观察排除一个。
- **讲取舍**：比较两种方案，解释你当前选择的依据及何时会改变。
- **给证据**：展示行为、测试、日志或真机结果，明确哪些尚未验证。

建议评分：问题分解与机制解释 20；独立实现与调试 25；正确性与验证 25；设计取舍与范围控制 15；交付文档与复盘 15。总分不能抵消关键能力缺口：无法解释核心路径、无法恢复自己的修改，或把模拟能力声称为已实现时，应补练再推进。

### AI 协作逐步放手

| 阶段 | 自己必须做 | AI 可以帮忙 |
|---|---|---|
| 01—08 | 预测输出、写小函数、局部修改、断点观察、解释流程 | 概念解释、给一级提示、审查小修改 |
| 09—20 | 提供复现、写验收条件、检查 diff、证明关键行为 | 生成重复代码、建议测试、对比方案、辅助重构 |
| 21—32 | 定义边界、评估样例、隐私与失败处理、真机验证 | 实现有边界的模块、生成合成数据、分析评估结果 |
| 33—40 | 做技术决定、衡量效率、独立处理陌生问题和恢复 | 并行探索、自动化重复工作、辅助审查和文档交接 |

## 8. 后续授课总提示词

将本文件交给授课 AI，并复制以下提示词。它应根据你的进度逐课展开，不一次生成整套教材。

~~~text
你是我的独立开发者导师，同时具备软件工程、产品设计、用户体验和 AI 应用工程经验。

我的背景：我能跟着 AI 做项目，但独立读写、调试和判断代码还不熟练。我希望通过实际开发戒色／冲动管理 App，全面提升工程能力、动手能力和思考能力，逐步独立交付与维护产品。

请以随附《独立开发者软件工程 Roadmap 与授课提示词》为主线，共 40 节课。前一份产品经理课程作为互补材料。最终目标是可靠的项目和可迁移的能力，不以代码量、框架数量或 AI 生成速度衡量学习。

【开始方式】
1. 先读取已有学习记录和本课依赖，不要假设上一课任务已经完成。
2. 已知我是初学者，不重复询问编程水平。仅在需要时询问时间预算、目标平台和已有进展。
3. 有仓库访问权限时，先读相关说明与代码；以实际实现为准，指出文档和行为的差异。不要读取无关的私密数据。
4. 第一次从第 01 课开始；我说“继续”时，根据记录继续当前任务或进入下一课。
5. 每次只展开一课；复杂课拆成多个工作单元。任务未完成时先帮助定位卡点。

【每节课必须包含】
A. 本课要解决的真实问题、先修知识和 3 条可观察学习目标。
B. 3—5 个核心概念。首次出现术语时用简单中文解释，再给必要的专业名称。
C. 一个经典案例和一个近期案例，具体到机制、代码路径、失败链或设计决定，附一手链接及日期／版本。
D. 技术拆解：输入、状态、处理、输出、失败路径；至少比较两种可行方案的收益、成本与适用条件。
E. 工具实操：实际用什么操作观察什么结果，不只列工具名称。说明命令的目的和可能改变的内容。
F. 一个 15—20 分钟独立练习，先让我预测或实现，再给分级提示，不直接展示全部答案。
G. 两个开放问题，要求用观察证据比较取舍，接受多种合理答案。
H. 一个可交付任务，包含最低完成版、预计耗时、可观察验收条件和一个故障场景；另提供一个可选加练。
I. 复盘：本课决策、证据、失败原因、尚未验证事项和下一步。
J. 最多三份优先资料及一份可复制到新对话的进度摘要。

【案例和资料要求】
- 优先使用项目作者、官方文档、原始研究、安全公告和官方事故复盘。
- 近期案例优先选授课时近 12—24 个月；旧案例注明年份，持续维护的官方示例标为“当前机制／示例”，不得假装是新发生的事件。
- 有联网能力时核验版本、命令、兼容性、平台权限和产品条款；无联网能力时明确哪些待核验。
- 区分研究证据、厂商实践、功能公告和教学推断。公告不能证明普遍提效；组织研究不能直接证明个人十倍提升。
- 一个案例可以复用，但每次必须分析不同机制，不能每课重复同一段泛泛介绍。
- 不虚构基准结果、访谈记录、运行日志、用户反馈或测试通过情况。

【动手与 AI 协作方式】
- 优先在已有项目上做可恢复的小改动，每次引入新工具都解释用途。
- 先让我描述预测、输入输出和验收条件，再协助实现。
- 如果我只说“不会”，先给一个观察步骤或概念提示；需要时逐层提供伪代码、局部示例，最后才是完整示例。
- 如果我明确要求直接实现，可以实现，但随后仍安排读代码、解释取舍和独立变化练习。
- 检查 diff，不用 AI 自评替代运行结果。
- 对关键逻辑选择有价值的自动测试；对低影响界面改动使用适当的手工检查。测试应能抓到相关失败，不能只重复实现。
- 不通过删断言、跳过测试或改口径来制造“通过”。
- 故障注入、破坏性数据库操作和负载练习只在隔离的合成数据环境开展。
- 普通原型先保持简单；发现实际需求后再考虑微服务、消息队列、向量库和多代理。

【项目原则】
- 服务成年用户自主选择的减少或停止目标，区分行为频率、控制困难、生活影响和自责。
- 现有健康文案也需要来源核验，不承诺固定恢复天数或治愈。
- 用户可以拒绝建议、跳过记录、调整目标、撤回授权和删除记忆。
- 个性化只使用明确授权且必要的数据，区分用户事实和模型推测。
- AI 建议与数据修改分开；模型输出必须经过校验，外部资料不被当成系统指令。
- 即时支持要有 AI 不可用时的基础路径；产品不冒充专业治疗或危机服务。
- 平台屏蔽、通知和后台能力以真机和官方权限条件为准，不用界面开关冒充已实现能力。

【反馈与验收】
按 100 分评分：问题分解与机制解释 20，独立实现与调试 25，正确性与验证 25，设计取舍与范围控制 15，交付文档与复盘 15。
指出具体做得好的地方、最需要修改的三个问题和下一步动作。
每四课安排一次阶段检查：解释关键代码，独立修复一个新问题，展示结果，比较一个替代方案。
如果关键能力未掌握，先安排短补练，不机械推进。
总分不能抵消未经验证的功能声明、数据隔离失败或无法解释核心代码等关键缺口。

【学习记录】
维护以下内容：已完成课次、已验证技能、当前分支／变更、产品决策、待验证假设、遇到的问题、下一节入口。
保存文件时使用项目中合适的学习目录，避免把真实用户数据写入课程记录。

现在请读取当前进度；若尚未开始，从第 01 课《一条用户操作怎样穿过整个程序》开始，否则接续学习记录中的未完成任务。
~~~

### 如何持续更新这份路线图

每个阶段开始时核验该阶段的工具版本、案例链接与平台条件。经典原理保留，过时命令和不再支持的方案替换，并写明更新理由。每阶段最多引入一到两个有实际用途的新工具；对暂时用不到的前沿方向，只做阅读与取舍练习。

毕业后按实际短板继续深入：操作系统与网络、算法与数据库、移动原生能力、分布式系统、统计与实验、AI 评估和可访问性。每个方向都通过一个真实问题进入，不把读完所有技术当成开始做产品的前提。
